The hand-off worklist

Verified

I booked a real appointment through the patient site. It appeared immediately on the desk under To enter in Klinique as DH-KZHFK8 — patient, phone, age, gender, doctor, date, time, fee and reason, each with its own copy button, plus Copy all.

The tick is the part that matters. Without a record of what has already been transferred, the only way to know is to search Klinique for each booking one at a time, and the failure that follows is a patient arriving at a clinic that never heard of them.

Automatic submission

Built, switched off

The code signs in to Klinique the way a browser does — fetching the form, carrying its CSRF token and session cookie — and posts each booking through it. 109 server tests exercise that path against a mock, so the driver is proven. The vendor integration is not.

Why it stays off

This is the hospital’s own finding, not a limitation of the code. Two live test submissions were attempted and neither created anything. They showed why blind automation is the wrong tool here:

  • The “Quick Registration” form posts to /visits/create_patient_with_emergency_visit — an emergency-visit path. Using it for ordinary website bookings risks flagging every one as an emergency.
  • The correct OP-appointment route is multi-step: pick doctor and date, load slots, then book. Automating it blind means reverse-engineering an AJAX flow against a live patient system.
  • Each guess is a write attempt at a real patient-creation endpoint. That is not a safe thing to iterate on, whatever the result.

If it is ever switched on, three hazards are now refusals rather than guesses. A doctor missing from the map is not submitted at all — Klinique’s physician field is a type-ahead over a directory far larger than Deepan’s roster, and an unknown value does not reliably bounce. Gender is only ever sent as a code the hospital has stated, because that form uses 1 = Female and 2 = Male, inverted from the obvious order. And the form’s “text the patient” checkboxes are set to off on every submit rather than being off by accident. All three are dormant today.

The embedded portal

Cannot verify here

The desk carries a Klinique tab so staff work in one window instead of two. The tab itself is fine: the address, the cookie warning, Reload and Open in a new tab all render and behave.

The frame below them is grey in this screenshot because the machine I tested on blocks deepan.klinique.net at the network level — I tried, and was refused before reaching them. So this says nothing about whether the embed works at the hospital.

Two things can break it, neither in the hospital’s control

  • Klinique’s framing headers. It currently sends no X-Frame-Options and no frame-ancestors, which is the only reason embedding is possible. If they ever add one, the frame goes blank with no warning.
  • Third-party cookies. Safari blocks them outright and Chrome is phasing them out. Where that bites, a sign-in inside the frame will not stick — the browser is enforcing that against Klinique’s origin, and no change to this app can alter it.

Because a cross-origin frame tells you nothing about itself from the outside, there is no way to detect a blank one and show a helpful error. So Open in a new tab is always on screen rather than hidden behind a failure state — staff are never stuck.

The one test worth running

Open the desk on a machine at the hospital and click the Klinique tab. If the portal appears, the embed works on your network and browser. If it stays grey, use Open in a new tab — it works the same and keeps staff signed in.

Nothing else needs deciding today. The worklist carries every booking either way, and it is the path the hospital is already using.
